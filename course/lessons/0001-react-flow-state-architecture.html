Mission Checkpoint: 架构搭建

Lesson 1: React Flow 与状态架构设计

欢迎来到构建类似 ComfyUI 或 tapNow 的节点编排系统的第一课。在开始编写业务逻辑前，我们需要在架构层面解决一个核心矛盾：视图与逻辑的耦合。

为什么不能只用 React Flow 的 State？

React Flow 提供了一套非常直观的 nodes 和 edges 状态管理。大多数初学者会直接将业务数据（比如节点的配置参数、执行结果）塞进 React Flow 节点的 data 字段中。这在简单应用中是可行的。

但我们的目标是实现 工作流断点 (Workflow Breakpoints)——即执行引擎能够在任意节点挂起，并能将当前状态序列化保存到数据库。如果我们把业务数据与包含 x, y 坐标、拖拽状态的视图数据混杂在一起，会导致：

  • 序列化成本极高：保存进度时必须剥离庞大的 UI 坐标和 DOM 状态。
  • 职责不清：执行引擎不应该关心某个节点在屏幕的左边还是右边。
  • 难以实现断点恢复：从数据库读取状态恢复时，合并 UI 状态与逻辑执行状态极其困难。
核心原则：双层状态架构 (Dual-State Architecture)

在复杂的节点编排系统中，状态必须一分为二：

  1. 逻辑状态层 (Logical Graph)：纯粹的数据模型，包含业务节点的层级、参数和连线关系。它是执行引擎 (Execution Engine) 运行的唯一事实来源。
  2. 视图状态层 (UI State)：由 React Flow 维护的展示层状态，包含坐标、缩放比例、节点宽高。它仅仅是逻辑层在二维平面上的“投影”。

使用 Zustand 实现状态分离

作为熟练的 React 开发者，我们使用 Zustand 来构建这个“真相之源 (Single Source of Truth)”。React Flow 组件只是 Zustand 数据的消费者。

// store.ts (简化版架构示例)
import { create } from 'zustand'
import { Node, Edge } from 'reactflow'

interface OrchestratorState {
  // 1. 视图状态 (UI State)
  uiNodes: Node[];
  uiEdges: Edge[];
  
  // 2. 逻辑状态 (Logical State) - 引擎直接操作这一层
  workflowDAG: Map<string, BusinessNode>;
  executionState: 'idle' | 'running' | 'suspended';
  
  // 3. Action: UI 变更时同步逻辑层
  onNodesChange: (changes) => void;
  // 4. Action: 业务逻辑引起 UI 变化
  updateNodeData: (id, newData) => void; 
}

当我们要执行工作流并触发“断点挂起”时，执行引擎只需提取并序列化 workflowDAG 和 executionState，而无需处理庞大的 uiNodes 坐标数组。

🛠 知识固化测验

在双层状态架构中，如果一个“等待用户输入”的节点触发了工作流断点 (Workflow Breakpoint) 导致系统挂起，系统保存到数据库的上下文应该只包含视图层状态还是逻辑层状态？
