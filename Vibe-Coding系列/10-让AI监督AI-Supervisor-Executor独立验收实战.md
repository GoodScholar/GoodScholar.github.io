# 别让同一个 AI 验收自己：用 Supervisor / Executor 建立独立验证闭环

AI 说“已完成”时，最该问的不是“它有没有再检查一遍”，而是：**谁在检查，检查的人看过实现过程吗？**

同一条线程里追加一句“请严格自查”，常常只能得到更长的自我证明。真正需要独立验收时，要隔离的是上下文和职责，而不只是把提示词写得更严厉。

上一篇刚开始从真实需求构建 Agent，下一步就会遇到一个更工程化的问题：当 Agent 已经能连续推进任务，怎样确认它交付的不是“看起来完成”，而是“有证据可复核”？

这篇给出一个最小闭环：**Coordinator 冻结任务契约，Executor 实现并提交证据，Supervisor 在独立上下文里核验。**它不替代普通自检；它只用于你需要把“完成”变成可审计结论的时刻。

## 严格提示词，为什么仍然不等于独立审查

同一个 Agent 刚写完方案、修改和测试，再让它“从最挑剔的角度检查”，它仍知道自己为什么这么写、哪些命令已经跑过、哪些假设曾被采纳。

这份上下文很有价值，但也容易让复查沿着原路径走：需求被默认已经覆盖，未运行的验证被理解成“应该能通过”，边界条件被原来的设计理由解释掉。

**问题不是 AI 自检没有价值，而是它不能单独承担高后果的验收。**低风险改动里，同线程验证往往是成本合理的选择；当任务涉及生产数据、凭据、安全、不可逆迁移、外部发布，或用户明确要求独立验收时，才值得增加一道隔离的审查。

OpenAI Docs 把 Subagents 描述为可由 Codex 启动、完成专门任务并回收结果的工作流；文档也提醒，并行子代理会消耗更多模型与工具资源。这里要抓住的不是“多开几个 Agent”，而是**为验收保留一个没有参与实现推理的入口**。[OpenAI Docs：Subagents](https://developers.openai.com/codex/subagents)

并行写作和独立验收不是一件事。前者解决的是把互不依赖的工作拆开；后者解决的是“谁来重新对照需求、亲自核验证据”。一个并行 Agent 如果拿着实现者的摘要直接点头，仍然不算独立验收。

## 三个角色：谁做事，谁下结论

这套流程里有三个角色，职责要故意分开。

**Coordinator：冻结靶子。**它澄清目标、允许写入范围、验收标准和升级条件，然后把这些内容固定为任务契约。它不替审查者相信执行者的结论。

**Executor：完成受限范围内的工作。**它按契约改文件、生成产物、运行命令，并提交真实的执行报告。它可以自测，但不能把“自测通过”当作独立验收。

**Supervisor：只读地核验。**它拿到任务契约、当前工作区、执行报告和证据包，在新的上下文中重新读交付物、查看差异、运行必要的只读检查。发现问题时提出可复现的返工意见，而不是直接代替 Executor 修改。

OpenAI Docs 对 Skills 的定位是：将指令、资源和可选脚本打包成可复用工作流。`supervisor-executor-review` 则是在这个能力之上定义的一套**本地自定义 Skill 协议**：角色分工、交接物、状态机与返工上限并不是 OpenAI 官方强制规范。[OpenAI Docs：Skills](https://developers.openai.com/codex/skills)

## 三份交接物：不要只传一句“做完了”

独立性并不靠“换一个窗口”自动出现。没有可复核输入，新的 Supervisor 只能猜测。

### 任务契约：把“做什么”变成可判断的靶子

任务契约至少写清目标、允许修改的文件、明确不做什么、逐条 AC、验证方式，以及需要人工升级的边界。

AC 要能回答“符合还是不符合”。“质量要高”不是 AC；“封面文件存在、不是 WebP、尺寸符合平台要求”才是。

可直接复用这份最小模板：

```text
目标：
范围：允许写入……；明确不做……

AC-001：
AC-002：

验证：要运行或人工核对的命令/检查。
升级条件：授权外写入、外部发布、凭据、付费、破坏性操作等。
```

它的作用不是把执行者限制得更死，而是给后续审查留下同一把尺子。契约不清楚时，应该停在 `BLOCKED` 请求澄清，而不是让 Executor 自行补完需求。

### 执行报告：把“我做了”换成可复现证据

执行报告至少包含：改动文件、授权范围核对、每条 AC 的实现位置、实际命令与退出码、原始输出、未完成项和风险。

一条合格的证据不是“已测试”，而是类似这样：

```text
命令：sips -g pixelWidth -g pixelHeight public/covers/cover-xxx.jpg
退出码：0
输出：pixelWidth: …；pixelHeight: …
```

这样 Supervisor 才能复跑或复核，而不是接受一段摘要。执行报告也要保留失败：失败输出能说明限制在哪里，比把问题藏在“完成”两个字里更有用。

### Supervisor Report：把意见变成状态和下一步

监督报告按 AC 逐条给状态、证据、严重级别和下一步。它不是一篇泛泛的代码评语。

- **`PASS`**：该条 AC 有独立、可复核的证据。
- **`REWORK`**：发现了明确且可修复的问题；反馈应说明位置、复现方式、最小修改和验证方式。
- **`BLOCKED`**：需要用户决定、额外权限、不可用依赖或改变任务范围。
- **`UNVERIFIED`**：证据缺失或环境无法验证。它不是“应该没问题”的委婉写法。

这里有一个容易被忽略的纪律：**没有证据，只能是 `UNVERIFIED`。**不要因为执行报告写得完整，就把它当作 PASS。

## 自动闭环：返工不是无限循环

一次完整的流程可以很短：契约冻结后派发 Executor；证据包齐全后，派发全新 Supervisor；若返回 `REWORK`，将逐条反馈交回原 Executor；补齐新证据后仍由原 Supervisor 复审。

同一个问题最多返工两轮，是这套自定义 Skill 的止损边界。两轮之后仍无法解决，状态应升级为 `BLOCKED`，交给人判断需求、权限或环境，而不是让两个 Agent 无限互相改写。

这个闭环有两个权限边界：Supervisor 默认只读；Coordinator 不因为“想快一点”扩大 Executor 的写入范围。涉及删除、覆盖数据、迁移、密钥、隐私、生产写入、对外发送或付费调用时，应该立即暂停并人工升级。

## 常见失败：看起来像监督，其实没有验收

### 未隔离上下文

**触发场景：**让同一条实现线程“切换成资深 Reviewer”。

**看到的现象：**审查结论不断引用自己的设计理由，而不是重新核对 AC 和实际输出。

**根本原因：**实现假设与审查输入混在一起，角色只换了称呼。

**实际处理：**让 Supervisor 使用新上下文，只接收任务契约、工作区、执行报告和证据包，不接收执行者的思考过程。

**验证结果：**Supervisor 能从 AC 开始复核，并在报告中给出自己查看的文件和命令。

**怎么避免：**把“是否有独立上下文”写进任务契约。

### 只传“已完成”摘要

**触发场景：**Executor 只汇报“功能已完成、测试已过”。

**看到的现象：**Supervisor 无法确认改了什么、跑了什么、哪些检查实际失败过。

**根本原因：**摘要丢掉了可复核的输入。

**实际处理：**补充 diff、命令、退出码、原始输出和未决风险；缺失时标记 `UNVERIFIED`。

**验证结果：**Supervisor 可以独立复跑或检查同一份证据。

**怎么避免：**在执行报告模板里把这些字段设为必填。

还有三种常见误用，也值得在启动前排除：Supervisor 直接修改交付物，责任链会断；无证据就 PASS，会把猜测伪装成验证；把多个 Agent 并行写作当成独立验收，会漏掉最后那次按 AC 回看的动作。

## 哪些任务值得付出这道成本

适合启动独立验收的信号包括：任务会触碰生产数据、凭据或安全边界；改动不可逆；需要对外发布；交付物跨多个步骤，且最终必须能审计；或者需求本身明确要求由独立角色验收。

不适合的信号同样重要：普通拼写修正、低风险格式调整、一次性只读问答，以及不产生可交付物的头脑风暴。把这些小任务也套上双角色流程，只会把简单问题变得迟缓。

你的最小判断可以只有一句：**如果这次出错后，我需要向别人解释“依据什么放行”，就准备独立证据包；否则先用单线程验证。**

## 可以立刻复制的验收清单

派发前，检查这几件事：

- 目标和“不做什么”是否写清。
- 每条 AC 是否可判断、可验证。
- Executor 的允许写入范围是否明确。
- 哪些动作必须升级给人，是否已经列出。

Executor 完成后，检查：

- 是否有改动文件与 diff 摘要。
- 每条 AC 是否有实现映射。
- 命令、退出码和真实输出是否齐全。
- 失败、限制与风险是否如实保留。

Supervisor 放行前，检查：

- 是否在独立上下文中亲自读过交付物。
- 是否按 AC 给出 `PASS`、`REWORK`、`BLOCKED` 或 `UNVERIFIED`。
- 每个 PASS 是否有可复核证据。
- 是否没有越权修改 Executor 的产物。

这份清单不是为了增加一次形式上的审批，而是让每一个放行结论都能回到可复核的证据。

## 示意案例：空邮箱为什么不能只看单元测试

> **示意案例（非真实项目结果）：**下面只演示交接物和判断如何工作，不代表某个真实项目的测试、耗时或审查结论。

假设要修复“注册接口接受空邮箱”的 Bug。任务契约把验收标准写成：空邮箱必须返回 `400`，并且有覆盖该行为的测试。

Executor 修改邮箱校验，提交改动位置、测试结果和接口验证证据。独立 Supervisor 不只看“校验函数已加”的摘要，而是检查真实路由是否调用了这段校验。

它发现校验没有接入注册路由，接口仍可能返回成功，于是标记 `REWORK`。Executor 把校验接入路由并补充集成验证；Supervisor 复核请求路径与证据后，才标记 `PASS`。

这个例子里，关键不是多加一个 Reviewer，而是把“函数存在”与“用户实际请求被拦住”拆成两件需要证据的事。

真正让 AI 变得更可靠的，不是让它更自信地说“我检查过了”，而是让另一条独立的工作流能够说清：**我看了什么、跑了什么、为什么这条 AC 可以放行。**

如果你正在把 Coding Agent 接进更重要的流程，可以先拿上面的最小契约和清单做一次小范围演练：选择一个能验证、也允许返工的任务，把“完成”换成一份证据包。
