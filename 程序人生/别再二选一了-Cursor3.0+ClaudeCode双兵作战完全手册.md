## 一个让我改变工作方式的真实经历

上个月我接了一个活：给一个 Flutter 项目的设置页做全面改版——UI 要重新设计，底下的状态管理要从 Provider 迁移到 Riverpod 3.x，顺带把网络层的错误处理统一重构。

**第一天，我只用 Cursor。**

UI 部分很顺滑——Cursor 的 Tab 补全 + Inline Chat 让我写 Widget 像打字一样快。但到了重构状态管理的环节，事情开始不对劲了：修改涉及 37 个文件，全局的 Provider 引用要一个一个找、一个一个换。Cursor 的上下文窗口在处理这种"全仓库级别的搜索→分析→替换"时显得力不从心，改到第 20 个文件我已经开始头疼了。

**第二天，我只用 Claude Code。**

状态管理迁移变得简单了——我在终端里跟 Claude Code 说："把所有 Provider 迁移到 Riverpod 3.x 的 Notifier 模式，保持 API 不变"，它自己读了全量代码，列出了迁移计划，然后一个一个文件改过去，改完自动跑测试。37 个文件，20 分钟搞定。但回头做 UI 微调的时候，没有可视化预览，全靠文字描述"这个间距大了 4px""那个圆角改成 12"，来回改了 6 轮还不满意。

**第三天，我两个一起用。**

Cursor 负责 UI 打磨，Claude Code 负责逻辑重构。**两小时，全部搞定。**

这三天的经历教会我一个道理：

> **不是 Cursor 不行，也不是 Claude Code 不行——是你非要让画笔干锤子的活。**

## ⚡ 2. Cursor 3.0 刚更新了什么？3 个改变游戏规则的功能

4 月 2 日刚发布的 Cursor 3.0 不是小版本迭代——它从"代码编辑器"变成了"代理管理控制台"。三个核心新功能值得你立刻上手：

### 🎯 功能一：Agents Window（代理窗口）

之前 Cursor 的 AI 交互在一个 Composer 面板里，一次只能跑一个对话。现在完全不同了：

```
┌────────────────────────────────────────────────────┐
│              Agents Window                         │
├──────────┬──────────┬──────────┬──────────────────  │
│ Agent #1 │ Agent #2 │ Agent #3 │ Agent #4           │
│ 本地开发  │ 云端重构  │ Worktree │ 远程SSH            │
│ 状态:运行 │ 状态:完成 │ 状态:运行 │ 状态:等待           │
├──────────┴──────────┴──────────┴──────────────────  │
│  [多代理并行：本地·云端·Worktree·SSH]                  │
└────────────────────────────────────────────────────┘
```

**核心能力：**
- 同时运行多个 Agent，每个跑在不同环境（本地、云端、Git Worktree、远程 SSH）
- 本地 Agent 要出门？一键把会话迁移到云端继续跑，人走了 AI 照干
- 不同 Agent 之间互不干扰，改崩了一个不影响其他的

**实战场景：** 你在 Agent #1 里写新功能，同时 Agent #2 在云端跑集成测试，Agent #3 在一个独立 Worktree 里尝试另一种实现方案——三件事同时推进。

### 🎨 功能二：Design Mode（设计模式）

这是前端开发者的救星。

之前你想让 AI 改 UI，得这么说："把登录按钮往右移一点，上面的间距大了，圆角再小一些"。AI 改完一看——不对，又改，又不对，改了 5 轮还在对齐。

现在？按 `Cmd+Shift+D` 开启 Design Mode，直接在 Cursor 内置浏览器里：

1. **点击**你想改的 UI 元素
2. **标注**具体想要的修改（拖拽间距、框选区域）
3. AI 自动拿到元素的组件路径、计算后的样式和周围上下文
4. **一次精准修改**，不用来回描述

> 一图胜千字，一次点击胜 5 轮 Prompt。

### 🏆 功能三：/best-of-n 多模型竞赛

当你不确定哪种实现方案最好时：

```bash
# 在 Agents Window 中使用
/best-of-n "实现一个无限滚动列表，要有加载动画和错误重试"
```

Cursor 会：
1. 在多个隔离的 Git Worktree 中同时启动任务
2. 让不同的模型（GPT-5、Claude、Gemini）各出一份方案
3. 生成对比视图，让你侧边查看每个方案的代码差异
4. 你挑最好的那个，一键合并

被选中的代码会被 merge 过来，其他的 Worktree 自动清理。**像面试候选人一样筛选代码。**

## 🔧 3. Claude Code 的独门绝技：4 个 Cursor 做不到的事

Claude Code 没有花哨的 GUI，但它在几个关键场景上的能力是 Cursor 根本比不了的。

### 🧠 绝技一：全仓库深度推理

Cursor 的上下文受限于你打开的文件和 @ 引用的内容。Claude Code 不一样——你给它一个指令，它会自己决定读哪些文件，自己画出依赖关系图。

**真实场景：** 我的 Node.js 项目突然出现了一个"幽灵 Bug"——API 偶发返回空数据。用 Cursor 我需要手动一个文件一个文件地找、猜、试。切到 Claude Code：

```bash
> 生产环境偶发出现 /api/activities 返回空数组的问题，
  正常情况下应该有数据。请分析可能的原因。
```

Claude Code 自己做了这些：
1. 读取路由定义 → 找到 Controller → 追踪到 Service 层
2. 分析数据库查询逻辑 → 发现 Redis 缓存的 TTL 设置
3. 检查并发场景 → 定位到缓存击穿的竞态条件
4. 给出修复方案 + 自动修改 + 跑测试验证

全程 8 分钟。我手动来起码 2 小时。

### 🔄 绝技二：大规模跨文件重构

这是 Claude Code 的天赋技能树。举个真实例子——我要把 Flutter 项目的 37 个文件从 Provider 迁移到 Riverpod：

```bash
> 将项目中所有 ChangeNotifierProvider 迁移到 Riverpod 3.x 的
  AsyncNotifier 模式。
  规则：
  1. 保持现有 API 接口不变
  2. 用 ref.watch 替换 Provider.of
  3. 迁移完成后运行 flutter test 验证
```

Claude Code 输出：

```
分析完成：
- 发现 37 个文件包含 Provider 引用
- 12 个 ChangeNotifier 类需要迁移
- 4 个嵌套 Provider 需要特殊处理

开始迁移...
[1/12] UserNotifier ✅
[2/12] ActivityNotifier ✅
...
[12/12] SettingsNotifier ✅

运行测试：41 passed, 0 failed
迁移完成。
```

你用 Cursor 一个文件一个文件改，改到天黑都改不完。

### 🖥️ 绝技三：Computer Use（操控 GUI）

Claude Code 最新上线了 Computer Use 功能——它可以直接操控你的屏幕：打开应用、点击按钮、截图验证。

```bash
> 打开 Chrome 访问 localhost:3000，
  点击登录按钮，验证登录流程是否正常，
  截图保存测试结果。
```

这在自动化 E2E 验证时极其有用——不用写 Selenium 脚本，不用配 Playwright，用自然语言直接操控 GUI 做端到端测试。

### 📚 绝技四：/powerup 交互式学习

新版 Claude Code 的 `/powerup` 命令直接在终端里开互动教程——带动画、带引导、带实操：

```bash
claude> /powerup
# 选择一个能力方向学习：
# 1. 上下文管理
# 2. 权限与安全
# 3. 子代理协作
# 4. Hooks 自动化
```

不需要去翻文档。边学边用，效率拉满。

## 🛠️ 5. 实战：一个 Feature 的双兵工作流

理论说够了，来看一个从头到尾的真实案例：**给应用新增"活动详情页"**，包含 UI、业务逻辑、API 对接和测试。

### 阶段一：用 Cursor 搭骨架（10 分钟）

```
1. 在 Cursor 中打开项目
2. 使用 Agents Window 创建新 Agent
3. 描述需求："创建一个活动详情页，包含头部 Banner、活动信息卡片、
   报名按钮、参与者列表"
4. AI 生成组件结构和基础 UI
5. 启用 Design Mode 微调布局
   - 点击 Banner → 调整高度比例
   - 点击报名按钮 → 修改圆角和颜色
   - 框选卡片区域 → 增大内边距
6. 预览确认 UI 效果 ✅
```

**产出**：页面骨架 + 打磨后的 UI 代码

### 阶段二：用 Claude Code 做逻辑（15 分钟）

```bash
# 切到终端
claude> 为活动详情页实现以下业务逻辑：
1. 对接 GET /api/activities/:id 获取活动详情
2. 实现报名功能，对接 POST /api/activities/:id/join
3. 用 Riverpod AsyncNotifier 管理状态
4. 添加错误处理：网络错误显示重试、活动已满显示等待
5. 复用项目中已有的 useRequest hook 和 ApiService

# Claude Code 自动：
# → 读取现有的 ApiService 找到 HTTP 封装方式
# → 创建 ActivityDetailNotifier
# → 在页面中注入状态管理
# → 添加错误边界和加载状态
# → 生成对应的单元测试
```

**产出**：完整的业务逻辑 + 状态管理 + 错误处理 + 测试

### 阶段三：回到 Cursor 做联调（5 分钟）

```
1. 在 Cursor 中查看 Claude Code 生成的代码（Git Diff 视图）
2. 运行项目，在内置浏览器中检查页面
3. 用 Design Mode 做最终的视觉微调
4. 确认一切正常后提交
```

**产出**：完成的 Feature，可直接提 PR

### 全程计时

| 阶段 | 工具 | 时间 | 做了什么 |
|------|------|------|---------|
| 骨架 + UI | Cursor | 10 分钟 | 组件结构 + 样式打磨 |
| 业务逻辑 | Claude Code | 15 分钟 | API 对接 + 状态管理 + 测试 |
| 联调收尾 | Cursor | 5 分钟 | 预览 + 微调 + 提交 |
| **合计** | **双兵配合** | **30 分钟** | **完整 Feature** |

如果只用一个工具？保守估计 1.5-2 小时。

**我的三个判断：**

1. **"单工具打天下"的时代结束了。** 就像你不会只用一把螺丝刀装修整个房子，AI 编程也不应该只靠一个工具。Cursor 和 Claude Code 各有不可替代的优势，搭配使用才是正确姿势。

2. **MCP 将成为第三根支柱。** 目前这两个工具各自为战，但 MCP 协议正在把它们连起来——未来你在 Cursor 里调起的 Agent 直接就能通过 MCP 访问数据库、CI 系统、日志平台。（这个话题我会在下一篇文章详细展开。）

3. **开发者的核心竞争力正在转移——从"写代码的速度"变成"编排 AI 的能力"。** 你不再需要打字最快，你需要的是知道什么时候用什么工具、怎么给 AI 定义清楚的边界和目标。

## 一句话总结

> **Cursor 管你看到的，Claude Code 管你看不到的。前者是你的眼睛，后者是你的大脑——瞎了看不见路，没脑子不知道往哪走。两个都要。**

## 快速上手行动指南

```bash
# 1. 安装 / 更新 Cursor 3.0
# 官网下载：https://cursor.com
# 确认版本 ≥ 3.0

# 2. 安装 Claude Code
npm install -g @anthropic-ai/claude-code

# 3. 在项目根目录创建共享配置
cat > AGENTS.md << 'EOF'
## 项目规范
- 框架：[你的框架]
- 语言：TypeScript strict
- 代码风格：[你的规范]
- 测试：[你的测试框架]
EOF

# 4. 开始双兵作战！
# → UI/日常编码：打开 Cursor
# → 重构/调试/测试：打开终端，输入 claude
```

别再纠结"用哪个"了。答案是——**两个都用，各施所长。**
