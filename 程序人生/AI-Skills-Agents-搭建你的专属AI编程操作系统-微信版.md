# 每次给 AI 写 300 字 Prompt？我搭了个体系，再也不用了

> 🚀 深度用下来，把 AI、Skills 和 Agents 串成了一套完整的工作流。开发效率明显提升，最关键的是——我终于不用每次都给 AI 写几百字的"小作文"了。

---

## 你可能正在经历的事

你打开 Cursor，对着 AI 说："帮我加一个用户登录功能。"

AI 给你写了一版。你一看：

```
❌ 组件库用了 Material，你项目用的是 Flutter Cupertino
❌ 状态管理用了 Provider，你项目统一用 Riverpod
❌ API 调用写了硬编码，你项目有统一的 dio 封装
❌ 文件放在了 lib/pages/ 下，你的约定是 lib/features/
```

你叹口气，在 Prompt 里加了一堆说明，重新跑一次。好了一些，但路由命名又不对了。

第三次，你把所有约定都塞进 Prompt 里。AI 终于生成了接近正确的代码——但你的 Prompt 写了 300 字，比生成的代码还长。

**第二天你又要加一个新功能。又要重新写 300 字的 Prompt。**

这就是没有体系的日常。

---

## 🎯 核心认知：三者不是替代关系，而是协作关系

很多人以为 AI、Skills、Agents 是三种工具，选一个就行。但实际上，它们是一套系统的三个层次：

| 层次 | 角色 | 能力边界 | 类比 |
|:---:|:---|:---|:---:|
| **AI** | 大脑 | 理解需求、做决策、生成思路 | 项目经理 |
| **Skills** | 工具箱 | 具体操作能力（规范、审查、测试） | 程序员 |
| **Agents** | 手脚 | 执行 Skills、协调流程、处理复杂任务 | 流程引擎 |

**关键洞察**：

- 没有 Skills 的 AI → 只会空谈，写出来的代码不符合规范
- 没有 Agents 的 Skills → 只是摆设，不知道什么时候用哪个
- 没有 AI 的 Agents → 只是脚本，不会根据需求做决策

三者缺一不可。

## 🔧 第一步：用 AGENTS.md 给 AI 装上"操作系统"

这是最容易被忽略但最关键的一步。

AGENTS.md 是放在项目根目录的一份指令文件，AI 在每次对话开始时自动读取它。

### 我的 AGENTS.md 结构

```markdown
## 项目基本信息
- 名称：Flutter AI Demo
- 框架：Flutter 3.x + Dart 3.x
- 状态管理：Riverpod 2.x
- 路由：GoRouter
- 网络请求：Dio

## 代码规范
- 文件命名：snake_case
- 类命名：PascalCase
- 常量命名：UPPER_CASE_SNAKE_CASE
- 行宽：不超过 120 字符
- 必须加文档注释

## 目录结构
```
lib/
├── features/          # 功能模块
│   ├── auth/          # 认证模块
│   └── home/          # 首页模块
├── common/            # 公共代码
│   ├── utils/         # 工具函数
│   └── widgets/       # 公共组件
└── providers/         # Riverpod 状态管理
```

## API 规范
- 统一使用 dio 封装
- Base URL：从环境变量读取
- 错误处理：统一拦截器

## 测试规范
- 每个功能模块至少 3 个单元测试
- Widget 测试覆盖关键交互
```

**效果**：从此 AI 生成的代码，自动符合你的项目规范，不用每次都提醒。

## ⚡ 第二步：用 Skills 打造你的"能力矩阵"

Skills 是把你的经验和规范封装成可复用的模块。

### 我的 Skills 库

我整理了 6 个核心 Skills，覆盖开发全流程：

| Skill | 职责 | 使用场景 |
|:---:|:---|:---|
| **规范检查** | 代码风格、命名、格式 | 每次代码生成后 |
| **代码审查** | 架构合理性、性能问题 | PR 提交前 |
| **测试生成** | 单元测试、Widget 测试 | 功能完成后 |
| **API 对接** | 请求封装、响应处理 | 接口开发时 |
| **路由管理** | 路由配置、页面跳转 | 页面开发时 |
| **状态管理** | Provider 定义、状态更新 | 状态逻辑开发时 |

### 一个 Skill 的示例

以「规范检查」Skill 为例：

```markdown
## 代码规范检查 Skill

### 检查项
1. 文件命名是否为 snake_case
2. 类命名是否为 PascalCase
3. 是否超过 120 字符行宽
4. 是否有未使用的 import
5. 是否缺少文档注释

### 处理方式
- 发现问题：列出问题清单，给出修改建议
- 严重问题：拒绝生成，要求修改后重试
```

## 🤖 第三步：用 Agents 构建你的"工作流引擎"

Agents 是把 Skills 串联起来的执行器。

### 我的需求处理 Workflow

```
用户提出需求
    ↓
AI 分析需求类型
    ↓
┌─────────────────────────────────────────┐
│          根据需求类型路由                │
├─────────────────────────────────────────┤
│ 纯前端页面 → 路由 Skill → 状态管理 Skill │
│             → 规范检查 Skill            │
├─────────────────────────────────────────┤
│ API 对接 → API Skill → 测试生成 Skill   │
│          → 规范检查 Skill               │
├─────────────────────────────────────────┤
│ 完整功能 → 路由 → 状态 → API → 测试      │
│          → 规范检查 → 代码审查           │
└─────────────────────────────────────────┘
    ↓
交付最终代码
```

### 条件分支示例

```yaml
workflow: requirement_to_code

steps:
  1. analyze_requirement:
      prompt: 分析需求类型，判断需要哪些 Skills
  
  2. route:
      conditions:
        - if: "包含页面跳转"
          then: [route_skill, state_skill]
        - if: "包含接口调用"
          then: [api_skill, test_skill]
        - if: "复杂功能"
          then: [route_skill, state_skill, api_skill, test_skill, review_skill]
  
  3. execute_skills:
      run: ${route_result}
  
  4. final_check:
      run: [style_check_skill]
```

## 📊 效果对比

### 搭建体系前

```
需求："帮我加一个用户登录功能"

实际工作流：
1. 写 300 字 Prompt 说明项目规范
2. AI 生成代码（不符合规范）
3. 手动修改代码（改命名、改目录、改 API 调用）
4. 手动写测试
5. 手动检查代码风格
6. 提交代码

耗时：约 2 小时
```

### 搭建体系后

```
需求："帮我加一个用户登录功能"

实际工作流：
1. 直接说需求
2. AI 自动读取 AGENTS.md
3. Agents 自动调用路由 + 状态 + API + 测试 Skills
4. 生成符合规范的完整代码
5. 规范检查 Skill 自动检查
6. 提交代码

耗时：约 1 小时
```

**搭建体系后，同类需求的处理时间明显缩短。**

## 💡 3 个常见坑点

### 坑点 1：Skills 太多反而变慢

**现象**：你建了 20 个 Skills，AI 每次都要读完所有文件，反而比直接写 Prompt 慢。

**原因**：没有路由机制，AI 不知道该读哪些。

**解法**：用 Agents 的条件分支，只在需要时加载对应的 Skills。

### 坑点 2：AI 忽略 AGENTS.md

**现象**：写了详细的 AGENTS.md，但 AI 生成的代码还是不符合规范。

**原因**：AGENTS.md 太长，AI 注意力被摊薄。

**解法**：把 AGENTS.md 拆成多个文件，每个文件专注一个领域。

### 坑点 3：Agents 做不了复杂决策

**现象**：遇到需要权衡的决策，Agents 总是选最保守的方案。

**原因**：Agents 的决策能力取决于 AI 的推理能力。

**解法**：关键决策点保留人工确认，不要完全依赖自动化。

## 📋 从 0 到 1 搭建清单

如果你想从零搭建自己的 AI 编程操作系统，按这个顺序来：

1. **第 1 周**：写好 AGENTS.md，定义项目基本规范
2. **第 2 周**：整理 3-5 个核心 Skills（规范检查、代码审查、测试生成）
3. **第 3 周**：设计 1-2 个常用 Workflow（纯前端页面、API 对接）
4. **第 4 周**：试运行，收集反馈，优化 Skills 和 Workflow
5. **持续迭代**：根据新需求不断补充 Skills
